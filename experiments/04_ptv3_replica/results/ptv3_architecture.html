How Point Transformer V3 reads a scene

PTv3 is the encoder behind Sonata. It turns a whole Replica scene into a few thousand feature tokens. This page walks through each step with a 2D toy room and the numbers we measured on Replica.

Step 01Input and embedding

The 1 cm Replica cloud is first thinned to one point per 2 cm grid cell. For room_0 that leaves 444,744 points; apartment_0 has 2.1 million. The scene is shifted so its xy-center is at 0 and its floor at z = 0.

Each point carries 9 numbers: position (x, y, z), color (r, g, b, scaled to [-1, 1]) and normal (nx, ny, nz). Each point also keeps its integer grid cell, which later steps use for neighbor lookups.

The embedding is a single linear layer, followed by LayerNorm and GELU, that maps the 9 numbers to 48 features per point. It looks at one point at a time; neighbors only come in during the blocks.

Step 02Serialization: from a cloud to a sequence

Full attention between 445k points would mean about 2·1011 pairs. PTv3 avoids that by sorting points along a space-filling curve: a path through the grid that visits every cell once and mostly steps between neighbors. Points close in the sorted list are then usually close in space.

The sorted list is cut into patches of 1024 consecutive points, and attention runs only inside each patch. Each colored region on the right is one patch.

The order only decides which points share a patch. Inside a patch, attention does not use the sequence positions at all; spatial layout reaches the features through the convolution in each block (step 03).

A curve sometimes jumps, so a patch border can separate two real neighbors. Sonata therefore uses four orders: z and hilbert curves, each also with x and y swapped (-trans). Consecutive blocks use different orders, so patch borders move and information crosses them.

Step 03One block

Every stage is a stack of identical blocks. A block keeps the number of points and channels; it only updates each point's features. Each of the three operations adds its result to the features it received (a residual connection), so a block can never destroy information, only add to it.

Step 04Grid pooling between stages

After each stage, points that fall into the same 2 × 2 × 2 cell of a twice-as-coarse grid are merged into one. Their features pass through a linear layer (the channel count doubles) and are max-pooled; their coordinates are averaged.

The network remembers which fine point went into which coarse point. That is what lets features be copied back to every input point later, and what our viewer uses for its "token" coloring.

Because a patch always holds 1024 points, a coarser grid makes the same patch cover a larger area: from roughly 0.6 m at stage 0 to about 10 m at stage 4. Early stages see detail, late stages see the whole room.

Try it: step through the levels. Cells are colored by the object most of their points belong to; a cell that mixes objects gets an amber outline.

Most of the computation sits in stage 3 (12 blocks). Patch area ≈ 1024 × cell², for points that lie on surfaces. Full inference: 0.08 s and 1.4 GB for room_0, 0.38 s and 5.0 GB for apartment_0 (RTX 5090, bf16).

Step 06Output and unpooling

Sonata is encoder-only: its output is the coarsest stage, 1,496 tokens with 512 features each for room_0.

To get a feature for every input point, walk the pooling record backwards. The recommended per-point feature concatenates the token features of stages 4, 3 and 2 (512 + 384 + 192 = 1,088 values) and copies them down to each 2 cm point. One more lookup (inverse) maps them back to the original 1 cm points.

Step 07What Sonata adds

Sonata is this exact architecture, 108.5M parameters, with weights learned without labels on a large collection of indoor and outdoor point clouds (on the order of 140k scenes). It is trained by self-distillation: the network must produce matching features for differently cropped and augmented views of the same scene.

In our zero-shot test on Replica, nearby points of the same instance were only slightly more similar in Sonata features than in a randomly initialized PTv3 (distance-controlled AUC ≈ 0.72 for both). Pretrained features usually show their value once a head is trained on top, so this does not settle the question.

Step 08Use in our SQ model

Replica scene→ PTv3 / Sonata→ tokens of stage 2 or 3→ farthest-point sampling → N queries→ decoder: self- + cross-attention→ SQ params + existence
  • The decoder's queries cross-attend to tokens of one stage. Stage 4 covers only 46–73% of instances, stage 3 70–82%, stage 2 81–98%, so stage 2 or 3 is the safer source.
  • Queries start at token positions picked by farthest-point sampling, so their number can grow with the scene size instead of a fixed 256.
  • The pooling record gives a point-to-token assignment for free at every stage, useful for the loss and later for grouping SQs.
