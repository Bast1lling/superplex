Almost every comparison so far was made at lr 1e-4, which badly under-trains the model. Their directions (e.g. "union loss helps existence", "3 decoder layers hurt") may not survive at a working learning rate. Only the learning rate itself, width 256 + 2 layers and the union losses were also run at 3e-4. Single seeds throughout, so the noise level is unknown.

Legend for the priority column: 1 next, 2 after the new baseline is fixed, 3 later / for generalization. Step costs: measured (code/component_latency.py, results/component_latency.md; noise about ±5 ms) unless marked ≈ (estimated from the per-part profile).

Proposed protocol

  1. Fix the optimization first (group A): lr sweep 1e-3 / 2e-3 / 3e-3 (+ warm-up variants), on the default top-k model. Pick the best, call it the new baseline.
  2. Measure the noise: the new baseline with 3 seeds. Differences below about 2 standard deviations are not interpreted.
  3. One-at-a-time ablations from the new baseline, highest priority first. Removing components (does it matter?) and adding components (does it help?) are both one run each. 3 runs in parallel keep the GPU busy; a 16-frame run takes 10–18 min.
  4. Combine what helps, check the combination with seeds, then — and only then — a full run to see whether it generalizes.
